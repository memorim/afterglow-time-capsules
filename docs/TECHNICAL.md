# Afterglow — цифровые капсулы времени

Сервис цифровых капсул времени. Сообщение шифруется, хранится до выбранной даты и открывается только правильным паролем после серверной проверки срока.

## Инженерные особенности

- AES-256-GCM со случайными 16-байтной солью и 12-байтным IV для каждой капсулы, 16-байтным тегом;
- ключ получается из пароля через `scrypt`, пароль не хранится;
- публичный API никогда не возвращает ciphertext, IV или auth tag;
- преждевременное открытие блокируется HTTP-статусом `423 Locked`;
- SQLite, Zod и интеграционные тесты;
- адаптивный интерфейс с countdown-состояниями.

Две открытые demo-капсулы используют пароли `light` и `orbit` — подсказки отображаются в интерфейсе.

## Запуск

```bash
pnpm install
pnpm start
```

Откройте `http://localhost:4800`. На Windows доступен `start-local.cmd`.

```bash
pnpm test
```

## Текущий режим работы
Шифрование выполняется на сервере: это AES-256-GCM, не end-to-end. Сервер получает пароль и текст запроса. Параметры scrypt закреплены: N=16384, r=8, p=1, ключ 32 байта, maxmem=32 МиБ. Они совпадают с прежними параметрами Node.js, поэтому сохранённые сообщения совместимы. Изменённые шифротекст, соль, IV или тег не проходят проверку подлинности.

API предназначен одному локальному оператору: loopback-соединения, разрешённые Host и проверка Origin изменяющих запросов. `HOST=0.0.0.0` не поддерживается. Метаданные каталога не разделяются по аккаунтам. Счётчики попыток ограничены памятью одного процесса: создание 10/мин, открытие 30/мин; превышение возвращает 429 и Retry-After. Ответы API имеют Cache-Control: no-store.

Время берётся с сервера. Новые даты нормализуются в UTC; прежние начальные строки без часового пояса трактуются как UTC. До срока API возвращает 423, в точности в срок — разрешает проверку пароля. Некорректная дата в БД даёт 503, а не раннее раскрытие. Перезапуск не меняет сохранённый срок, но корректность зависит от системных часов сервера. Это серверная политика доступа: обладатель БД и пароля может расшифровать текст вне приложения раньше срока. Метаданные даты не входят в authentication tag; защита от администратора с правом изменения БД не заявляется.

Схема и начальное заполнение создаются одной транзакцией `BEGIN IMMEDIATE` с busy_timeout=5000. Существующая пустая таблица не засеивается заново. Вставка капсулы — одна атомарная SQL-операция; ошибки не оставляют частичных строк. Журнал ошибок не содержит сообщения, пароля или SQL. Резервные копии БД нужно защищать на уровне файловой системы. Автоматического удаления и восстановления доступа нет.
